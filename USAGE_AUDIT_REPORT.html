ISR (Incremental Static Regeneration) Optimization

✅ MAJOR COST REDUCTION: ISR ceiling increased from 1 hour to 24 hours
  • Previous: 3,600 second ceiling = 1 page rebuild/hour per article
  • Current: 86,400 second ceiling = 1 page rebuild/day per article
  • Trigger: Webhook GROQ filter eliminates false positives (no viewCount-only syncs)
  • Cost impact: 24x reduction in redundant cache invalidations

Query Complexity Issues Found

Issue #1: Unlimited Article Fetches in Category Pages

🔴 PROBLEM: queryArticleByCategory has no limit on article count
src/lib/sanity/lib/queries.ts (line ~500)
  • Fetches ALL articles in a category (could be 100+)
  • Each article includes full body (Portable Text)
  • Multiplied by number of category page views
  • Impact at scale: 50+ articles × category pages = very expensive
Fix: Add [0..50] pagination limit
Estimated savings: 50-100+ API calls/month at scale

Issue #2: Music Artist Nested Subqueries

⚠️ HIGH COST: queryMusicArtistBySlug contains expensive nested subqueries
src/lib/sanity/lib/queries.ts (line ~343)
  • Inline songs query: Fetches 0..99 song objects
  • Inline albums query: Fetches 0..49 album objects
  • Both with full reference expansion
  • Only hit occasionally, but very expensive when accessed
Fix: Move to pagination or lazy-load related content
Estimated savings: 50-100 API calls/month when scaled

Issue #3: Timeline Event Reference Expansion

⚠️ MEDIUM COST: queryTimelineEventBySlug expands multiple references
src/lib/sanity/lib/queries.ts (line ~657)
  • Each timeline event references related articles, live events, other timelines
  • All references are expanded inline
  • Multiple nested expansions increase query complexity
Fix: Use projection to fetch only IDs, lazy-load on demand
Estimated savings: 50+ API calls/month
